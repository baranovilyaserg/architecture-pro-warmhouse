# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удалённо включать/выключать отопление в своих домах.
- Система поддерживает включение/выключение отопления в домах.

**Мониторинг температуры:**

- Пользователи могут просматривать текущую температуру в своих домах через веб-интерфейс.
- Система поддерживает получение данные о температуре с датчиков, установленных в домах.

### 2. Анализ архитектуры монолитного приложения

Архитектура приложения представляет из себя синхронный монолит на Go с СУБД Postgres.  Всё управление идёт от сервера к датчику. Данные о температуре также получаются через запрос от сервера к датчику. При старте датчик регистрируется в сервере.

### 3. Определение доменов и границы контекстов

**Выделенные домены:**
- Домен базы данных.
- Домен мониторинга температуры.

**Границы контекстов:**
- Контекст управления датчиками температуры.
- Контекст мониторинга температуры. 

### **4. Проблемы монолитного решения**

- Для подключения новых устройств необходим выезд специалиста.
- Для добавления новый функций необходимо обновление основного сервера и бд.
- Синхронное взаимодействие станет узким местом при большом кол-ве обращений.
- Слабая отказоустойчивость. Сбой в сервере или бд повлечет остановку работы всей системы.
- Сложность в организации работы команды над одним большим приложением. Что повлечет уменьшение производительности.
- Сложность в масштабировании отдельных частей монолита.

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql

Для проверки можно использовать Postman коллекцию smarthome-api.postman_collection.json и вызвать:

- Create Sensor
- Get All Sensors

Должно при каждом вызове отображаться разное значение температуры

# **Задание 6. Разработка MVP**

## Описание реализованных микросервисов и их интеграции

### devicecomponent (Python, FastAPI)
- Отвечает за хранение и предоставление информации об устройствах (девайсах) и их телеметрии.
- При старте создает таблицы devices и telemetry в общей базе Postgres, добавляет для примера взаимодействияустройства bulb и gate.
- REST API для CRUD по устройствам и телеметрии (OpenAPI: [devicecomponent.yaml](/api/devicecomponent.yaml)).
- Подписывается на WebSocket devicecontroller и сохраняет получаемую телеметрию в БД.
- [Postman коллекция для тестирования](/api/examples/devicecomponent.postman_collection.json)

### devicecontroller (Go)
- Получает список устройств с devicecomponent через REST API при старте.
- Генерирует телеметрию по каждому устройству (эмулирует работу устройств).
- Отправляет телеметрию в WebSocket (порт 42200, endpoint /ws), на который подписан devicecomponent.
- REST API для отправки команд на устройства и получения сгенерированной телеметрии (OpenAPI: [devicecontroller.yaml](/api/devicecontroller.yaml)).
- [Postman коллекция для тестирования](/api/examples/devicecontroller.postman_collection.json)

### Интеграция с монолитом
- Монолитное приложение (smart_home) продолжает работать с БД Postgres, в которой devicecomponent создает и обновляет таблицы устройств и телеметрии.
- Монолит может обращаться к REST API devicecomponent для получения информации об устройствах и их телеметрии.
- devicecontroller и devicecomponent интегрированы через WebSocket (devicecontroller -> devicecomponent) и REST (devicecontroller -> devicecomponent).

### Протоколы и спецификации
- [OpenAPI спецификация devicecomponent](/api/devicecomponent.yaml)
- [OpenAPI спецификация devicecontroller](/api/devicecontroller.yaml)
- [JSON Schema WebSocket протокола](/api/devicecontrollerwebsocketapi.json)
- [Пример сообщения телеметрии](/api/examples/telemetry-example.json)

### Плюсы текущей архитектуры
- Микросервисы изолированы по ответственности: devicecomponent — хранение и API, devicecontroller — генерация и отправка телеметрии.
- Снижение нагрузки на REST API за счет асинхронного WebSocket для передачи телеметрии.
- Есть тестовые коллекции для быстрой проверки API (Postman).

### Минусы и ограничения
- Нет брокера сообщений — взаимодействие только через REST и WebSocket, что не подходит для сложных сценариев.
- Нет обработки ошибок и повторных попыток при сбоях сетевого взаимодействия.
- Нет полноценной схемы миграций БД (создание таблиц только при старте).
- В devicecontroller отсутствует обработка изменений списка и параметров девайсов, сейчас список запрашивается при старте.

### Что доработать
- Вынести схему миграций БД в отдельный инструмент.
- Добавить брокер сообщений (RabbitMQ/Kafka) для масштабируемой передачи телеметрии.
- Реализовать обработку ошибок и повторные попытки при сетевых сбоях.
- Добавить в devicecontroller обработку изменения списка и параметров девайсов.
